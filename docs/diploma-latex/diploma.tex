В~рамках углублённой исследовательской части проведены шесть экспериментов: визуальный анализ внимания модели методом Grad"~CAM, оценка качества обучаемых представлений через t"~SNE/UMAP-проекции и~метрики разделимости, статистический анализ ручных признаков, калибровка апостериорных вероятностей методом temperature scaling, сравнение с~foundation-моделью CLIP в~режимах linear probe и~zero-shot, переход к~multi-label постановке задачи с~автоматической генерацией дополнительных меток.
Область применения -- системы курации цифровых фотоколлекций, обучающие материалы по~компьютерному зрению, исследовательские прототипы.

\chapternonum{Введение}

\textbf{Актуальность темы.} Цифровых фотографий с~каждым годом становится всё больше: профессиональные архивы, ленты социальных сетей и~каталоги стоковых агентств сегодня хранят миллиарды снимков. Разметить такие объёмы вручную невозможно, а~существующие системы автоматического тегирования распознают преимущественно объекты и~сцены -- <<кошка>>, <<здание>>, <<пляж>>. Эстетику кадра -- его настроение, цветовую палитру, контраст, характер освещения -- они почти не~описывают.

А~ведь именно стилистика чаще всего важна при~отборе изображений: для~дизайн-проектов, рекламных кампаний, художественных коллекций, да~и~просто личных архивов. За~последние годы методы глубокого обучения и~доступность предобученных моделей сделали стилевую классификацию решаемой даже на~небольшом датасете, собранном силами одного человека.

В~работе используется подход transfer learning: берётся свёрточная сеть, уже обученная на~миллионах изображений ImageNet, и~дообучается под~новую задачу. Это~даёт разумный баланс между качеством и~вычислительными затратами -- обучать сеть с~нуля при~нашем объёме данных было~бы и~бессмысленно, и~непозволительно дорого.

\textbf{Цель работы.} Разработать программный комплекс, который позволяет загружать фотографии, автоматически определять их~стиль с~оценкой уверенности модели, искать похожие изображения в~своей коллекции и~фильтровать галерею по~стилю. Вторая, исследовательская часть цели~--- разобрать обученную модель <<под лупой>>: проверить её~интерпретируемость, оценить качество выученных представлений и~устойчивость метрик.

\textbf{Задачи работы.}
\begin{enumerate}[label=\arabic{enumi})]
\item провести обзор современных методов классификации изображений, существующих программных продуктов-аналогов и~технологического стека; обосновать выбор архитектуры и~инструментальных средств;
\item собрать и~разметить датасет фотографий по~стилевым категориям; провести предобработку, балансировку и~дедупликацию;
\item обучить и~оценить нейросетевую модель классификации; провести несколько итераций пересмотра таксономии классов по~результатам диагностики;
\item спроектировать многокомпонентную программную архитектуру с~асинхронной обработкой запросов на~основе очереди сообщений и~объектного хранилища;
\item реализовать REST-API для~регистрации пользователей, загрузки изображений, получения результатов классификации, поиска по~стилю и~поиска похожих изображений;
\item реализовать клиентское веб-приложение;
\item обеспечить контейнеризацию и~автоматизированное развёртывание системы;
\item провести шесть углублённых исследовательских экспериментов: визуализацию внимания модели, анализ embedding-пространства, статистический анализ ручных признаков, калибровку вероятностей, сравнение с~foundation-моделью CLIP, расширение задачи до~multi-label;
\item сформулировать направления дальнейшего развития на~основе полученных результатов.
\end{enumerate}

\textbf{Объект исследования} -- автоматическая стилевая классификация цифровых фотографий. \textbf{Предмет исследования} -- архитектуры свёрточных нейронных сетей применительно к~задаче с~ограниченным обучающим набором и~субъективной таксономией классов, методы интерпретации их~поведения, способы согласования постановки задачи с~природой стилевых атрибутов.

\textbf{Методы исследования.} Подход transfer learning на~основе свёрточных нейронных сетей с~предобучением на~ImageNet; стратифицированное разделение данных с~детерминированным seed; двухфазное дообучение модели; weighted random sampling для~балансировки классов; cross-entropy и~binary cross-entropy loss; cosine annealing learning rate; визуализация активаций методом Grad"~CAM; снижение размерности эмбеддингов методами t"~SNE и~UMAP; статистический анализ распределений (ANOVA, тест Краскела-Уоллиса); калибровка вероятностей методом Guo et~al.\,(2017); линейный probe и~zero-shot классификация на~основе модели CLIP.

\textbf{Научная и~практическая новизна.} Научная составляющая -- адаптация подхода transfer learning к~задаче стилевой классификации с~субъективно определёнными классами; формальное обоснование операциональной определимости отдельных классов через статистики низкоуровневых признаков; экспериментальная демонстрация устойчивости качественных выводов (иерархия сложности классов, структура ошибок) к~случайному разбиению данных. Практическая -- завершённое программное решение с~открытым исходным кодом, готовое к~демонстрации и~расширению.

\textbf{Структура работы.} Помимо введения и~заключения, работа содержит шесть глав, список литературы и~приложения. Первая глава -- аналитическая: постановка задачи, обзор методов, выбор архитектуры и~технологического стека, сравнение с~существующими продуктами. Вторая и~третья посвящены проектированию системы и~деталям реализации. Четвёртая глава -- про данные и~обучение: как собирался датасет, как пересматривалась таксономия классов и~что показали три итерации обучения. Пятая глава, самая объёмная, -- это тестирование и~шесть исследовательских экспериментов. Шестая разбирает развёртывание, безопасность и~то, куда работу можно развивать дальше. В~заключении я~свожу итоги и~достигнутые показатели.

\chapter{Аналитическая часть}

\section{Постановка задачи классификации}
\label{sec:problem}

Задачу можно ставить двумя способами. Первый, классический -- single-label: каждой фотографии присваивается ровно один стилевой ярлык. Второй, более общий -- multi-label: одному снимку может соответствовать сразу несколько стилей с~независимыми степенями уверенности. Я~начинал с~single-label как с~более простой и~привычной для~стандартных обучающих пайплайнов постановки, но~по~ходу анализа результатов (см.~гл.~\ref{ch:results}) пришёл к~выводу, что~для~стиля она в~принципе неверна, и~перешёл к~multi-label.

В~single-label выходом модели служит вектор $\hat{y} \in \R^C$ постмягкомаксных вероятностей ($C$~--- число классов), а~предсказанием -- $\arg\max_c \hat{y}_c$. В~multi-label выход -- вектор сигмоид-активаций, и~решение по~каждому классу принимается отдельно, по~подобранному порогу $\theta_c$.

Целевыми классами выбраны восемь визуальных стилей, операционально определимых через статистики низкоуровневых признаков изображения (см.~табл.~\ref{tab:classes}):

Этот набор сложился не~сразу -- он~прошёл через две итерации пересмотра (см.~гл.~\ref{ch:dataset}). Поначалу среди классов были \texttt{moody} и~\texttt{street}, но~оба пришлось убрать. \texttt{moody} постоянно перетекал в~\texttt{dark}, \texttt{dramatic} и~\texttt{vintage} и~не~поддавался чёткому определению; \texttt{street} же~оказался жанровой категорией (уличная съёмка), а~не~стилевой. Вместо них я~ввёл \texttt{monochrome} и~\texttt{neon} -- эти~два класса задаются строго, через насыщенность.

Классы я~старался подобрать так, чтобы они были по~возможности независимы в~пространстве низкоуровневых признаков; позже это~подтвердил статистический анализ (см.~раздел~\ref{sec:scorecard}). Но~на~уровне конкретного снимка совмещения всё~равно случаются: кадр запросто может быть одновременно \texttt{monochrome} и~\texttt{minimalist}. Именно это~в~итоге и~подтолкнуло меня к~multi-label (раздел~\ref{sec:multilabel}).

\section{Обзор методов глубокого обучения}
\label{sec:methods}

\subsection{Обучение модели <<с нуля>>}

Чтобы обучить глубокую свёрточную сеть со~случайной инициализации весов, нужны порядка $10^5$-$10^6$ размеченных изображений на~класс и~серьёзные вычислительные мощности. В~моём случае -- восемь классов и~датасет, собранный и~размеченный вручную -- это~нереально ни~по~объёму данных, ни~по~бюджету. Да~и~смысла нет: такое обучение игнорирует уже накопленные в~предобученных моделях представления.

\subsection{Feature extraction}

Промежуточный вариант: выходы предпоследнего слоя предобученной сети берутся как векторные признаки, а~поверх них обучается простой классификатор -- логистическая регрессия, SVM или~k-ближайших соседей. Считается это дёшево, но~потолок качества невысок: признаки ImageNet заточены под~объекты, а~не~под~стилевые атрибуты, и~подстроить их под~новую задачу нельзя -- веса полностью заморожены.

Этот подход я~использовал в~двух местах как точку отсчёта для~сравнения: feature extraction поверх ImageNet-весов EfficientNet"~B0 (раздел~\ref{sec:scorecard}) и~поверх замороженного CLIP ViT"~B/32 (раздел~\ref{sec:clip}).

\subsection{Fine-tuning (выбранный подход)}

Здесь классифицирующий слой заменяется на~новый, последние свёрточные блоки размораживаются, и~сеть дообучается на~целевом датасете с~пониженным learning rate. Представления подстраиваются под~стилевые признаки, но~при~этом сохраняется общая иерархия признаков, выученная на~миллионах картинок ImageNet. Для~датасетов среднего размера ($10^3$-$10^4$ изображений) это~золотая середина между качеством и~стоимостью -- именно поэтому я~остановился на~нём.

Схему fine-tuning'а я~сделал двухфазной. Сначала backbone полностью заморожен и~учится только классифицирующая голова, причём с~повышенным learning rate -- это~не~даёт функционалу потерь <<разболтаться>> на~старте. Затем все слои размораживаются, learning rate снижается и~включается cosine annealing. Детали -- в~разделе~\ref{sec:training}.

\subsection{Дополнительные техники}

Помимо fine-tuning'а, в~работе применены следующие техники, направленные на~стабилизацию обучения и~повышение качества:
\begin{itemize}
\item \textbf{WeightedRandomSampler} -- балансирующая выборка минибатчей с~весами, обратно пропорциональными частотам классов; нейтрализует bias предсказаний при~остаточном дисбалансе.
\item \textbf{Label smoothing} с~параметром $\varepsilon=0{,}1$ -- сглаживание истинной метки, препятствует переуверенности модели и~улучшает калибровку.
\item \textbf{Mixed precision training} (\texttt{torch.amp.autocast}) -- ускорение обучения на~GPU Tesla T4 в~1{,}5"~2 раза при~сохранении численной устойчивости.
\item \textbf{Early stopping} с~патиенсом семь эпох по~val~accuracy -- предотвращает переобучение и~экономит вычислительное время.
\item \textbf{Безопасные для~стиля аугментации}: RandomResizedCrop, HorizontalFlip, ограниченный ColorJitter (без~RandomGrayscale, без~сильного hue jitter). Аугментации не~должны уничтожать классифицирующий сигнал (например, RandomGrayscale превратил~бы любую фотографию в~\texttt{monochrome}, нарушив разметку).
\end{itemize}

Основным backbone я~выбрал \textbf{EfficientNet"~B0}~\cite{Tan:2019}, и~вот~почему.

\paragraph{Точность при~малом размере.} Параметров у~неё столько~же, сколько у~MobileNet"~V3 Large, но~на~ImageNet она точнее примерно на~2{,}5\,пп по~Top"~1. ResNet"~50 она~обгоняет на~$\sim$\,1{,}6\,пп, будучи при~этом в~пять раз меньше по~числу параметров. Секрет -- в~\emph{compound scaling}: глубина сети, ширина слоёв и~входное разрешение масштабируются согласованно, а~не~по~отдельности.

\paragraph{Быстрый инференс на CPU.} Чекпоинт весит 16~МБ, одно предсказание на~обычном процессоре занимает около 50~мс. Это~значит, что~в~production можно обойтись без~GPU -- развёртывание проще, а~эксплуатация дешевле.

\paragraph{Готовая реализация.} В~\texttt{torchvision.models} сеть поднимается одной строкой: \verb|efficientnet_b0(weights=EfficientNet_B0_Weights.IMAGENET1K_V1)|. Не~нужно ничего собирать руками, и~экспериментировать становится заметно быстрее.

Для~честности сравнения я~дополнительно обучил \textbf{ResNet"~50} (результаты -- в~разделе~\ref{sec:training}), а~совсем другую парадигму -- visual transformer -- проверил отдельно на~CLIP ViT"~B/32 (раздел~\ref{sec:clip}).

\section{Обзор существующих программных продуктов}
\label{sec:competitors}

Прямого аналога -- продукта, который автоматически тегирует фотографии именно по~стилю, -- на~рынке я~не~нашёл. Существующие решения закрывают смежные ниши, но~расходятся с~моей задачей по~ключевым признакам: степень автоматизации, открытость модели, фокус на~стиле (а~не~на~содержимом), возможность self-hosting.

\paragraph{Pinterest, Are.na, Cosmos.} Платформы визуального discovery и~ручной курации коллекций. Pinterest использует автоматическое распознавание объектов через внутреннюю модель Pinterest Lens (одежда, мебель, еда), но~таксономия стилей в~явном виде отсутствует; теги генерируются пользователями. Are.na и~Cosmos автоматической классификацией не~занимаются вовсе -- ценность платформ в~человеческом отборе.

\paragraph{Google Photos, Apple Photos.} Встроенные в~экосистемы платформы автоматической классификации фотографий пользователя. Распознают \emph{содержание} (объект, сцена), не~предоставляют API для~извлечения признаков или~таксономии стилей, не~допускают self-hosting.

\paragraph{Adobe Lightroom AI tagging (Adobe Sensei).} Профессиональный продукт с~автоматическим тегированием. Теги преимущественно технические (\emph{Low light}, \emph{Sharp}, \emph{High contrast}) или~предметные (\emph{Mountain}, \emph{Indoor}). Стилевые понятия (\emph{vintage}, \emph{moody}) присутствуют, но~их~надёжность не~декларируется метриками -- это маркетинговая функция платной подписки. Модели и~внутренняя реализация закрыты.

\paragraph{Системы style transfer (Prisma, DeepArt, Lensa AI).} Это generative-системы, решающие \emph{обратную} задачу: применение стилевых характеристик одного изображения к~содержимому другого. Концептуально полезны -- их~работоспособность подтверждает, что~стиль есть вычислимая характеристика, отделимая от~содержимого, но~задача классификации в~них не~ставится.

\paragraph{Академические работы.} Стилевая классификация изображений -- устоявшаяся исследовательская задача с~собственными датасетами и~benchmark'ами:
\begin{itemize}
\item \textbf{AVA (Aesthetic Visual Analysis)}~\cite{Murray:2012} -- 250\,000 фотографий с~эстетическими оценками; используется для~aesthetic scoring, не~для~стилевой классификации.
\item \textbf{Flickr"~Style}~\cite{Karayev:2014} -- 80\,000 фотографий, размеченных по~20~стилям (HDR, Vintage, Bokeh, Macro и~др.); первая публично доступная модель стилевой классификации на~CNN.
\item Работы по~photographic style transfer~\cite{Luan:2017}, содержательно обсуждающие операциональное определение <<стиля>>.
\end{itemize}

Методологически я~опираюсь на~Flickr"~Style: та~же связка <<дискретная таксономия + supervised classification>>. Но~таксономию я~взял свою -- короче и~с~операциональными определениями восьми классов; за~счёт меньшего перекрытия категорий это~поднимает per-class качество.

\paragraph{Позиционирование.} В~итоге система занимает нишу, до~которой у~коммерческих продуктов руки не~дошли: \textbf{open-source, self-hosted классификатор фотоархива по~стилю с~публичным embedding-API}. Кому это~может пригодиться -- фотографам, дизайнерам, кураторам коллекций, исследователям компьютерного зрения, да~и~в~образовательных программах по~глубокому обучению.

\section{Обзор технологий программного стека}
\label{sec:stack}

Каждый компонент стека я~выбирал, сравнивая с~альтернативами по~трём критериям: зрелость экосистемы, эксплуатационные характеристики и~пригодность именно под~эту задачу. Разберу ключевые решения.

\subsection{Backend-фреймворк}

Здесь я~рассматривал Spring~Boot~3 (Java~17), Django REST Framework (Python), Express/Fastify (Node.js) и~Gin/Echo (Go). Остановился на~\textbf{Spring~Boot~3}.

Главным аргументом стало \emph{отделение от~Python-стека ML-сервиса}. Backend и~ML работают на~разных платформах с~разными зависимостями -- так~не~возникает конфликтов библиотек, и~каждый сервис масштабируется сам по~себе. Плюс у~Spring <<из~коробки>> есть зрелая Security-инфраструктура (фильтр-чейн, JWT, BCrypt), а~это~критичная и~легко ломающаяся при~самописной реализации часть. Ещё~один весомый плюс -- Testcontainers: PostgreSQL, RabbitMQ и~MinIO поднимаются в~Docker как настоящие сервисы прямо в~интеграционных тестах.

\subsection{ML-инференс}

\paragraph{Язык и веб-фреймворк.} Для~ML-сервиса я~взял \textbf{FastAPI} на~Python~3.11. Из~альтернатив был~Flask (по~умолчанию синхронный) и~production-тяжеловесы TorchServe и~Triton Inference Server, заточенные под~высоконагруженный GPU-инференс. Но~для~дипломной работы мне важнее была прозрачность кода -- я~должен видеть и~контролировать каждый шаг инференса, -- а~не~максимальная пропускная способность. FastAPI закрывает все потребности (HTTP"~API плюс фоновые consumer'ы AMQP) и~вдобавок сам генерирует OpenAPI-документацию.

\paragraph{Фреймворк глубокого обучения.} Тут выбор очевиден -- \textbf{PyTorch~2.4}. В~исследовательских публикациях после~2020 года он~стал стандартом де-факто (более 80\,\% статей CVPR~2023). На~практике это~значит огромный выбор предобученных моделей и~туториалов, а~\texttt{torchvision.models} отдаёт EfficientNet"~B0 с~ImageNet-весами буквально одной строкой.

\subsection{Очередь сообщений}

Кандидаты: RabbitMQ, Apache Kafka, Redis Streams, Amazon SQS, ZeroMQ. Выбрал \textbf{RabbitMQ}.

AMQP даёт ровно тот набор примитивов, который мне нужен: durable-очереди с~гарантированной доставкой, direct exchange с~routing keys, подтверждения обработки. Плюс management-UI, в~котором удобно отлаживать поток сообщений. Kafka для~сценария <<один producer -- один consumer>> с~низким TPS избыточна: её~козыри вроде партиционирования и~replay здесь не~нужны. Redis Streams пока~молода и~бедна на~маршрутизацию.

\subsection{Объектное хранилище}

Тут выбор шёл между MinIO, AWS~S3, локальной файловой системой и~Cloudinary. Я~взял \textbf{MinIO}.

Решающим оказалась \emph{совместимость с~API AWS~S3}: один и~тот~же SDK (\texttt{boto3} в~Python, \texttt{minio-java} в~Java) работает и~с~MinIO, и~с~S3. Если~понадобится перенести систему в~облако, достаточно поменять endpoint в~конфиге -- код~не~трогаем. Локальную файловую систему я~отбросил: нет~HA-гарантий, и~реплики backend'а не~смогут шарить файлы. Cloudinary -- закрытый сервис, self-hosting не~поддерживает.

\subsection{Реляционная база данных}

PostgreSQL~16, MySQL/MariaDB, MongoDB, SQLite -- из~них я~выбрал \textbf{PostgreSQL}.

Строгая типизация бережёт от~порчи данных, а~ACID-гарантии важны для~согласованности тройки \texttt{photos $\leftrightarrow$ photo\_styles $\leftrightarrow$ photo\_features}. Есть~и~задел на~будущее: когда понадобится ускорить поиск по~эмбеддингам, можно подключить расширение \texttt{pgvector} прямо здесь~же, не~меняя хранилище и~не~плодя новых сервисов.

\subsection{Клиентский фреймворк}

React~18, Vue~3, Angular, Svelte -- остановился на~\textbf{React~18 с~Vite~5}.

Честно говоря, по~чистым техническим характеристикам React не~лучший: у~Svelte и~Vue~3 меньше runtime и~полнее типизация. Но~React -- самая востребованная технология на~рынке, и~для~дипломной работы это~весомый образовательный довод. Vite~же~даёт мгновенный Hot Module Replacement и~dev-сервер, который запускается в~5-10 раз быстрее связки Webpack/CRA.

\subsection{Аутентификация}

Выбор был между JWT (stateless), серверными session-cookies и~делегированием OAuth2 стороннему провайдеру. Я~взял \textbf{JWT~(HS512, TTL~24~ч.)}.

Stateless-схема позволяет масштабировать backend горизонтально, не~заводя общего хранилища сессий. Отзыв токенов в~текущей версии не~реализован -- для~прототипа это~допустимо, а~в~production добавляется blacklist в~Redis или~короткие TTL с~refresh-токенами.

\subsection{Оркестрация развёртывания}

\textbf{Docker~Compose}. Kubernetes для~дипломной демонстрации был~бы из~пушки по~воробьям: одна команда \texttt{docker compose up} поднимает все~пять контейнеров в~правильном порядке и~в~общей сети. Если~дело дойдёт до~Kubernetes, образы переиспользуются как~есть -- допишутся лишь по~паре манифестов Deployment+Service на~сервис.

\section{Поток данных при классификации фотографии}
\label{sec:dataflow}

Проследим путь одной фотографии -- от~загрузки до~появления тегов в~галерее:

\begin{enumerate}[label=\arabic{enumi})]
\item Пользователь загружает файл изображения через React-форму запросом \verb|POST /api/photos| с~Content"~Type \verb|multipart/form-data| и~заголовком \verb|Authorization: Bearer <JWT>|.
\item Spring backend выполняет валидацию: проверка подписи JWT, проверка MIME-типа (whitelist \verb|image/jpeg|, \verb|image/png|, \verb|image/webp|), проверка размера (лимит~25~МБ через \texttt{spring.servlet.multipart}).
\item Файл сохраняется в~MinIO под ключом \verb|user-{userId}/{uuid}.{ext}|. Префикс с~идентификатором пользователя предотвращает горизонтальную утечку privileges, UUID гарантирует уникальность.
\item Создаётся запись в~таблице \texttt{photos} со~статусом \texttt{PENDING}.
\item Backend публикует сообщение в~exchange \verb|classification.exchange| с~routing key \verb|classification.task|, содержащее $\{photoId, s3Key, bucket\}$.
\item ML-сервис получает сообщение из~очереди \verb|classification.tasks|, скачивает файл из~MinIO по~$(bucket, s3Key)$, выполняет препроцессинг (resize до~256, центрированный crop до~$224\times 224$, нормализация ImageNet-статистиками) и~прямой проход через сеть.
\item Выход сети разделяется на~два потока: top"~3 стилевых ярлыка с~постмягкомаксными вероятностями и~1280-мерный embedding с~предклассифицирующего слоя.
\item Результат, обогащённый палитрой (5 цветов через k"~means на~уменьшенной копии) и~score"~card-метриками (5~детерминированных характеристик), публикуется в~очередь \verb|classification.results|.
\item Spring backend (consumer) получает результат и~в~рамках одной транзакции: удаляет прежние записи \texttt{photo\_styles} по~$photoId$, вставляет новые, сохраняет embedding в~\texttt{photo\_features}, переводит \verb|photos.status| в~\texttt{DONE}.
\item Клиент, выполняющий периодический опрос \verb|GET /api/photos| каждые три~секунды при~наличии \texttt{PENDING}-фотографий, получает обновлённое состояние и~перерисовывает галерею.
\end{enumerate}

На~практике весь цикл -- от~нажатия кнопки до~тегов в~галерее -- укладывается в~$2$-$3$ секунды для~файла около 2~МБ, и~это~на~CPU, без~всякого GPU.

\section{Модель данных}
\label{sec:datamodel}

Реляционная схема включает пять основных сущностей. Их~отношения отражены в~листинге~\ref{lst:schema}.

\begin{lstlisting}[caption={Схема реляционной модели данных},label=lst:schema,basicstyle=\ttfamily\small,frame=single]
users        (id PK, email UNIQUE, password_hash, created_at)
styles       (id PK, name UNIQUE)
photos       (id PK, user_id FK->users, s3_key UNIQUE,
              uploaded_at, status ENUM('PENDING','DONE','FAILED'))
photo_styles (photo_id FK->photos, style_id FK->styles,
              confidence DECIMAL(5,4),
              PRIMARY KEY (photo_id, style_id))
photo_features (photo_id PK/FK->photos, embedding TEXT,
                palette JSON, scores JSON, brightness REAL,
                contrast REAL, saturation REAL,
                warmth REAL, sharpness REAL,
                dominant_hex TEXT)
\end{lstlisting}

Статус фотографии -- это~конечный автомат на~три состояния: \texttt{PENDING} (загружена, ждёт в~очереди), \texttt{DONE} (классифицирована) и~\texttt{FAILED} (ML-сервис вернул ошибку или~истёк таймаут). Перейти можно только из~\texttt{PENDING} в~одно из~двух остальных -- ни~обратных, ни~боковых переходов нет.

Справочник \texttt{styles} наполняется при~старте миграциями Flyway (\texttt{V1\_\_init.sql}, \texttt{V2}, ..., \texttt{V6\_\_taxonomy\_v3\_8\_classes.sql}). Я~специально держу стили в~таблице, а~не~в~enum -- иначе каждая итерация таксономии требовала~бы правки и~пересборки Java-кода.

Эмбеддинг (\verb|photo_features.embedding|) сейчас лежит как JSON-строка из~1280~чисел. Когда коллекция вырастет за~$\sim$\,100\,000~снимков, я~планирую перейти на~расширение \texttt{pgvector}: тип столбца станет \texttt{vector(1280)}, а~поиск ближайших соседей пойдёт через HNSW-индекс. Пока~же поиск устроен проще -- брутфорсом в~Java-сервисе \texttt{SimilarityService} (cosine similarity, $O(N \cdot 1280)$). Для~коллекций до~$\sim$\,10\,000~фотографий это~отрабатывает менее чем за~50~мс, чего для~прототипа более чем достаточно.

\section{Аутентификация и авторизация}
\label{sec:auth}

Аутентификация -- на~JWT, без~серверных сессий. Пароли храню как BCrypt-хеши со~strength~10. При~успешном входе сервер выдаёт токен (подпись HS512, срок жизни 24~часа) с~email пользователя в~поле \texttt{sub}. Секретный ключ берётся из~переменной окружения \verb|JWT_SECRET|; в~репозитории \texttt{application.yml} лежит заведомо нерабочая заглушка \verb|change-me-in-prod| -- чтобы случайно не~уехать с~ней в~production.

Дальше каждый запрос несёт заголовок \verb|Authorization: Bearer <token>|. Фильтр \texttt{JwtAuthFilter} стоит в~цепочке перед \texttt{UsernamePasswordAuthenticationFilter}: он~достаёт токен, проверяет подпись и~срок, кладёт \texttt{UserDetails} в~\texttt{SecurityContext}. Важная деталь: доступ к~чужим ресурсам закрыт не~в~бизнес-логике, а~прямо на~уровне SQL -- репозиторий фильтрует по~\verb|user_id| (\verb|findByIdAndUserId|). Так~horizontal privilege escalation отсекается ещё~до~того, как~запрос дойдёт до~кода.

\section{Backend на Spring Boot}
\label{sec:backend}

\subsection{Управление схемой через Flyway и режим JPA validate}

Схему БД меняют только миграции Flyway из~\verb|backend/src/main/resources/db/migration/|. Hibernate я~держу в~режиме \verb|ddl-auto: validate|: на~старте он~сверяет сущности с~таблицами и~падает, если~что-то разошлось. Это~специально -- так~Hibernate не~сможет втихую поменять схему в~production, а~единственным источником правды о~структуре БД остаются миграции.

\subsection{Двойной клиент MinIO}

Тут~я~столкнулся с~неочевидной проблемой и~решил её~двумя бинами \texttt{MinioClient} с~разными endpoint'ами. Основной \texttt{minioClient} ходит на~\verb|http://minio:9000| (имя сервиса в~Docker-сети) и~делает всю~внутреннюю работу -- \verb|putObject|, \verb|bucketExists|, \verb|makeBucket|. А~вот \texttt{minioPresignClient} смотрит на~\verb|http://localhost:9000| с~жёстко заданным регионом \verb|us-east-1| и~нужен только для~генерации presigned-URL'ов, которые уходят в~браузер. Причина проста: браузер не~знает, что~такое \verb|minio:9000| внутри Docker-сети, поэтому в~URL должен стоять хост, доступный снаружи.

Фиксированный регион тут~критичен. Без~него SDK при~первом обращении лезет к~бакету за~\verb|GET ?location|, пытается достучаться до~\verb|localhost:9000| уже из~контейнера -- и~всё~падает. На~отладку этого у~меня ушло прилично времени.

\subsection{Асинхронная публикация через RabbitTemplate}

Для~задач классификации я~использую exchange типа \verb|direct| с~routing key. Сообщения сериализуются через \texttt{Jackson2JsonMessageConverter} -- в~итоге Python-консьюмер видит обычный JSON и~не~обязан понимать какие-либо Java-специфичные форматы.

Когда приходит результат, consumer на~стороне backend'а обновляет БД атомарно: сначала удаляет все~старые строки \texttt{photo\_styles} по~$photoId$ (с~\verb|flush()|, чтобы гарантировать порядок), потом вставляет новые. Это~страхует от~мусора при~повторной обработке (retry) -- иначе часть старых тегов могла~бы остаться висеть в~таблице.

\subsection{Обработка ошибок}

\texttt{GlobalExceptionHandler} с~аннотацией \verb|@RestControllerAdvice| унифицирует ответы при~неуспешных запросах. Это позволяет фронтенду полагаться на~единый формат и~централизовать обработку ошибок в~одном axios-interceptor'е.

\section{ML-сервис на FastAPI}
\label{sec:mlservice}

\subsection{Построение модели}

Архитектура модели создаётся вызовом \verb|efficientnet_b0(weights=None)| с~последующей заменой классифицирующего слоя:

\begin{lstlisting}[language=Python,basicstyle=\ttfamily\small,frame=single,caption={Создание модели и подключение весов},label=lst:model]
from torchvision.models import efficientnet_b0
model = efficientnet_b0(weights=None)
in_features = model.classifier[1].in_features  # 1280
model.classifier[1] = nn.Linear(in_features, len(self.styles))
\end{lstlisting}

Если~рядом лежит файл \verb|weights/efficientnet_b0_styles.pth|, в~модель подгружается \texttt{state\_dict} дообученных весов. Сами веса я~не~держу в~репозитории (\verb|.gitignore|) -- это~крупные бинарники со~своим жизненным циклом; они~лежат у~меня в~Google~Drive и~докидываются вручную при~деплое.

А~если~файла весов нет, сервис стартует в~\emph{эвристическом режиме}: считает статистики изображения (яркость, контраст, насыщенность, теплота, динамический диапазон) и~раскидывает их~по~классам набором взвешенных правил. Это~не~замена обученной модели -- просто способ прогнать всю~систему end-to-end, пока~весов ещё~нет под~рукой.

\subsection{Извлечение эмбеддингов и сплит forward-прохода}

Здесь кроется ключевой приём всей реализации: я~расщепляю прямой проход на~два этапа, чтобы за~один раз получить и~эмбеддинг, и~стилевые вероятности:

\begin{lstlisting}[language=Python,basicstyle=\ttfamily\small,frame=single,caption={Расщеплённый forward-проход},label=lst:fwd]
with torch.no_grad():
    x = self.transform(img).unsqueeze(0).to(self.device)
    feats = self.model.features(x)
    pooled = self.model.avgpool(feats)
    pooled_flat = torch.flatten(pooled, 1)        # [1, 1280] - эмбеддинг
    logits = self.model.classifier(pooled_flat)   # [1, num_classes]
    probs = torch.softmax(logits, dim=1)
    embedding = pooled_flat.squeeze(0).cpu().numpy()
\end{lstlisting}

Эмбеддинг я~снимаю прямо с~выхода global average pooling -- то~есть до~классифицирующей головы, -- а~голову применяю отдельной строкой. В~итоге оба выхода берутся за~один forward, и~эмбеддинг уезжает вместе с~результатом классификации, без~повторного прогона сети.

\subsection{Препроцессинг и аугментации}

Препроцессинг детерминированный, без~аугментаций: resize до~$224\times 224$ (точно, без~CenterCrop, чтобы сохранить пропорции), приведение к~\texttt{torch.float32} в~диапазоне $[0;1]$, нормализация ImageNet-статистиками ($\mu = [0{,}485; 0{,}456; 0{,}406]$, $\sigma = [0{,}229; 0{,}224; 0{,}225]$). Идентичный препроцессинг применяется и~при~обучении (см.~раздел~\ref{sec:training}), чтобы избежать train/serve skew.

\subsection{Цветовая палитра и score-card}

Помимо стилевой классификации, ML-сервис извлекает два дополнительных слоя описания изображения. Оба вычисляются детерминированно из~пиксельных статистик, без~участия нейросети.

\paragraph{Палитра цветов} -- 5 доминирующих цветов в~RGB через \texttt{sklearn.cluster.KMeans} (\verb|n_clusters=5|, \verb|n_init=3|) на~уменьшенной до~$100\times 100$ копии изображения. Кластеры сортируются по~размеру (наиболее частый цвет первым) и~возвращаются как hex-строки. Доминирующий hex-цвет дополнительно сохраняется в~\verb|photo_features.dominant_hex| для~быстрой фильтрации галереи по~цвету.

\paragraph{Score-card} -- 5 количественных метрик в~диапазоне $[0;1]$:

\begin{itemize}
\item \texttt{brightness} -- средняя perceptual luma $Y' = 0{,}299 R + 0{,}587 G + 0{,}114 B$;
\item \texttt{contrast} -- стандартное отклонение luma, удвоенное и~ограниченное на~$1{,}0$;
\item \texttt{saturation} -- среднее значение нормированной формулы $(max - min) / max$ в~RGB;
\item \texttt{warmth} -- нормализованная разность $R - B$ в~диапазон $[0;1]$;
\item \texttt{sharpness} -- средняя абсолютная величина градиента luma, как proxy для~резкости.
\end{itemize}

У~этих метрик двойное назначение. В~интерфейсе они~просто дополняют стилевые ярлыки наглядными числами. А~в~исследовательской части они~оказались куда важнее: через них~можно формально определить классы измеримыми статистиками (раздел~\ref{sec:scorecard}) и~использовать как baseline-признаки, чтобы понять, сколько~же реально добавляют глубокие представления поверх <<очевидных>> характеристик.

\subsection{AMQP-консьюмер в фоновом потоке}

Библиотека \texttt{pika} работает на~блокирующем соединении, а~это~не~дружит с~asyncio. Я~вынес consumer в~отдельный \texttt{threading.Thread} с~обработкой \texttt{AMQPConnectionError} (пауза 5~с -- и~новая попытка). Само~FastAPI-приложение поднимается независимо и~отдаёт \verb|/health| для~диагностики: имя модели, путь к~весам, устройство, список стилей.

Префетч очереди я~ограничил двумя задачами через \verb|channel.basic_qos(prefetch_count=2)|. Причина приземлённая: инференс одного изображения съедает около 500~МБ peak RSS, и~если~набрать задач больше, при~всплеске загрузок сервис словит OOM.

\section{Клиентское приложение на React}
\label{sec:frontend}

\subsection{Дизайн}

Галерею я~оформил в~тёмном brutalist-стиле: фон \verb|#111|, поверхности \verb|#141414|, акцент \verb|#c0392b|, никаких скруглений, типографика \emph{uppercase} с~широким трекингом и~мелким кеглем. Идея простая -- не~перетягивать внимание на~себя, а~отдать его~фотографиям, и~заодно подчеркнуть, что~это~рабочий инструмент, а~не~витрина.

\subsection{Masonry-сетка}

Галерея организована в~детерминированную masonry-сетку через CSS~Grid: \verb|grid-template-columns: repeat(6, 1fr)|, \verb|grid-auto-rows: 180px|, \verb|grid-auto-flow: dense|. Каждой ячейке на~основе её~индекса присваивается класс из~детерминированного паттерна (\verb|w2|, \verb|h2|, \verb|w2 h2|), что~создаёт визуально неоднородный ритм без~использования случайности. Опция \verb|dense| гарантирует, что~крупные ячейки не~оставляют пустот.

\subsection{Реактивный опрос статуса}

Сразу после загрузки фотография висит в~статусе \texttt{PENDING}. Клиент в~\verb|useEffect| раз в~три~секунды переспрашивает \verb|GET /api/photos|, пока в~ответе есть хоть~одна \texttt{PENDING}. Да, это~не~так элегантно, как~WebSocket или~SSE, но~я~сознательно выбрал polling: нагрузка на~сервер копеечная, кода -- несколько строк в~компоненте, и~не~нужно тащить ради этого отдельную инфраструктуру на~бэкенд.

\subsection{Axios-interceptor для централизованной обработки 401/403}

При~получении кодов 401 или~403 от~любого endpoint'а взаимодействия токен очищается из~\verb|localStorage|, и~пользователь перенаправляется на~маршрут \verb|/login|. Это унифицирует обработку истечения JWT без~дублирования логики в~каждом компоненте, обращающемся к~API.

\subsection{Модальное окно с похожими фотографиями}

Клик по~ячейке галереи раскрывает модальное окно: увеличенный снимок, цветовая палитра, score-card-метрики, top"~3 стилей с~прогресс-барами и~сетка из~шести похожих фотографий (запрос \verb|GET /api/photos/{id}/similar|). Похожесть считается как~cosine similarity между 1280-мерными эмбеддингами (раздел~\ref{sec:embed_quality}). Клик по~любой из~похожих открывает уже~её -- так~по~коллекции можно гулять не~по~тегам, а~по~визуальному <<сходству>>, что~ощущается куда живее.

\section{Инфраструктура развёртывания}
\label{sec:infrastructure}

\verb|docker-compose.yml| описывает шесть сервисов: \texttt{postgres}, \texttt{rabbitmq}, \texttt{minio}, \texttt{minio-init} (одноразовый инициализатор бакета при~первом запуске), \texttt{backend}, \texttt{ml-service}. Healthcheck'и и~зависимости через \verb|depends_on: condition: service_healthy| гарантируют корректный порядок старта. Все сервисы помещены в~общую Docker-bridge-сеть \texttt{psc-network}, что~обеспечивает разрешение имён хостов внутри.

Именованные тома \texttt{postgres\_data}, \texttt{rabbitmq\_data}, \texttt{minio\_data} держат данные между перезапусками контейнеров. Frontend для~production я~бы~упаковал в~отдельный nginx-контейнер, но~для~дипломной демонстрации он~запускается в~dev-режиме Vite через \verb|npm run dev| -- так~проще показывать и~править на~ходу.

\section{Сбор датасета}
\label{sec:collection}

Изображения я~брал с~Unsplash и~Pexels -- у~обеих платформ есть бесплатное API с~приемлемым лимитом запросов и~свободной лицензией. Выбор не~случаен: там~высокое техническое качество снимков и~широкий разброс стилей, а~для~стилевой классификации это~как~раз то, что~нужно.

Сбор шёл через скрипт \verb|01_dataset_collection.ipynb|, который дёргает Unsplash Search API и~Pexels Search API. Под~каждый класс я~придумал свой набор английских запросов -- скажем, для~\texttt{neon} это~<<neon photography>>, <<cyberpunk lights>>, <<synthwave aesthetic>>, <<tokyo neon>> и~ещё~несколько. API отдаёт по~30~картинок на~страницу, и~я~листал страницы, пока не~набиралось около 250~снимков с~каждого источника на~класс.

Каждому файлу я~приписывал префикс источника (\verb|u_| -- Unsplash, \verb|p_| -- Pexels) и~уникальный идентификатор: так~проще отлаживать и~отслеживать, откуда что~пришло. После первой итерации набралось около 1000~изображений на~класс, но~распределение вышло кривое -- от~491 в~\texttt{monochrome} до~1457 в~\texttt{minimalist}. Виновата разная популярность тематик в~стоковых архивах: <<минимализм>> снимают куда чаще, чем~чистую <<монохромную>> съёмку.

\section{Эволюция таксономии}
\label{sec:taxonomy}

\paragraph{v1.} Стартовый набор из~восьми классов: \texttt{moody}, \texttt{minimalist}, \texttt{street}, \texttt{golden\_hour}, \texttt{dark}, \texttt{airy}, \texttt{vintage}, \texttt{dramatic}. Обучил без~балансировки, прямо на~перекошенном датасете (max/min$=5{,}0$) -- и~получил val~acc$=0{,}678$. Модель при~этом откровенно сваливалась в~\texttt{minimalist}: предсказывала его~примерно в~2{,}5 раза чаще, чем~следовало.

\paragraph{v2.} Первым делом убрал \texttt{street}. Это~оказалась жанровая категория, а~не~стиль -- модель быстро нашла shortcut <<есть~люди на~улице~$\to$~\texttt{street}>> и~училась ему, а~не~визуальным признакам. Заодно включил балансировку через WeightedRandomSampler. Точность подросла до~$0{,}724$, но~теперь перекос переехал на~\texttt{moody}. Confusion matrix всё~объяснила: \texttt{moody} постоянно путается с~\texttt{dark}, \texttt{dramatic} и~\texttt{vintage}. То~есть это~не~самостоятельный, ортогональный класс, а~композитный -- и~операционального определения у~него попросту нет.

\paragraph{v3.} Тогда~я~убрал и~\texttt{moody}, а~вместо него ввёл два~класса, которые можно задать формулой: \texttt{monochrome} (saturation~$\approx 0$) и~\texttt{neon} (saturation~$\geq 0{,}6$ при~низкой средней яркости). Добавил двухфазную схему обучения и~MD5-дедупликацию. Результат -- val~acc=$0{,}726$ и~исчезнувший перекос: предсказания по~классам легли в~коридор $0{,}87$-$1{,}08$ от~истинных частот. По~per-class F1 лучшими стали \texttt{neon}~($0{,}926$) и~\texttt{golden\_hour}~($0{,}856$), а~слабым -- \texttt{monochrome}~($0{,}520$): он~определён только цветом и~потому пересекается с~композиционными классами (\texttt{minimalist}, \texttt{vintage}, \texttt{dark}).

\paragraph{v3.1.} То~же~самое, но~переобученное на~воспроизводимом split'е. Зачем это~понадобилось -- подробно в~разделе~\ref{sec:reproduce}; это~отдельная и, пожалуй, самая поучительная история всей работы.

\section{Предобработка и балансировка}
\label{sec:preprocess}

Перед обучением датасет проходит три~этапа обработки:

\begin{enumerate}[label=\arabic{enumi})]
\item \textbf{Cap по~количеству.} Каждый класс случайно урезается до~600 фотографий (с~фиксированным \texttt{random.seed(42)}). Самый раздутый \texttt{minimalist} (1457~снимков) после split'а дополнительно ужимается до~500. \texttt{monochrome} с~его~491~фото не~трогаю -- меньше у~меня и~так~нет.
\item \textbf{MD5-дедупликация.} Для~каждого файла в~классе считаю MD5-хеш содержимого и~оставляю только одну копию каждого. Всего так~ушло 102~дубликата -- больше всего в~\texttt{vintage} (25), \texttt{airy} (27) и~\texttt{dramatic} (17). Берутся они~оттуда, что~один и~тот~же снимок индексируется по~нескольким поисковым запросам сразу.
\item \textbf{Stratified split} 80/20 с~тем~же seed=42. Cap по~\texttt{minimalist} (500~файлов) применяется уже~внутри split'а -- получается 400~train / 100~val.

\section{Архитектура дообучения}
\label{sec:training}

EfficientNet"~B0 я~инициализирую ImageNet-весами и~дообучаю в~две~фазы:

\paragraph{Фаза 1 (только голова, 5~эпох).} Backbone полностью заморожен, учится одна новая голова \verb|Linear(1280, 8)| при~learning~rate $10^{-3}$. Смысл -- дать классификатору быстро подстроиться под~распределение классов, пока~backbone стоит на~месте. Если~разморозить всё~сразу, первые~же крупные градиенты от~случайно инициализированной головы могут <<разболтать>> аккуратно выученные на~ImageNet представления.

\paragraph{Фаза 2 (всё целиком, до~25~эпох).} Размораживаю все~слои, но~learning rate ставлю разный: $10^{-4}$ для~backbone и~$10^{-3}$ для~головы -- разница в~десять раз. Расписание -- CosineAnnealingLR с~$T_{\max}=25$. Добавляю label smoothing $\varepsilon=0{,}1$ (стабилизирует обучение и~улучшает калибровку) и~WeightedRandomSampler с~весами $1/count_c$ -- так~каждый класс попадает в~минибатч примерно одинаково часто.

\paragraph{Остальное.} Минибатч~32, оптимизатор AdamW (weight\_decay$=0{,}01$), mixed precision (\verb|torch.amp.autocast|), early stopping с~патиенсом 7~эпох по~val\_acc. Аугментации train: RandomResizedCrop(224, scale=(0.7, 1.0)), RandomHorizontalFlip(p=0.5), ColorJitter(brightness=0.15, contrast=0.15, saturation=0.15, hue=0.05). Val я~не~аугментирую вовсе -- иначе метрика перестанет быть честной.

\section{Воспроизводимость v3 и переход к v3.1}
\label{sec:reproduce}

Готовя исследовательскую часть (гл.~\ref{ch:results}), я~наткнулся на~неприятную методологическую проблему. Оригинальный split модели v3 лежал в~эфемерной файловой системе среды обучения и~после перезапуска просто пропал. Казалось~бы, не~беда -- сгенерирую заново с~тем~же \texttt{random.seed(42)}. Но~не~тут-то~было: порядок обхода файлов на~Drive (FUSE-mount) оказался нестабильным, и~\texttt{random.shuffle()} раскладывал снимки уже~иначе. Точное разбиение восстановить не~удавалось.

Заметил я~это~по~абсурдной метрике: та~же~самая модель на~<<восстановленном>> val выдала не~$0{,}726$, а~$0{,}925$. Per-class F1 скакнули совершенно неправдоподобно -- \texttt{monochrome} с~$0{,}545$ до~$0{,}876$, \texttt{dramatic} с~$0{,}586$ до~$0{,}897$, плюс 28-35~пп на~ровном месте. Это~классический отпечаток data leakage: часть снимков, на~которых v3 обучалась, после нового split'а попала в~val. Модель их~попросту запомнила и~теперь <<угадывала>> почти без~ошибок, раздувая метрику.

\textbf{Что я~сделал.} Переобучил модель с~нуля на~воспроизводимом split'е. Сам~алгоритм разбиения я~вынес в~скрипт \verb|training/make_split.py| и~зафиксировал порядок обхода файлов через \verb|sorted()| -- теперь при~том~же seed=42 split всегда один и~тот~же. Гиперпараметры оставил идентичными v3. Эти~веса и~стали финальными -- v3.1.

\textbf{Что получилось.} val~acc$=0{,}694$, macro F1$=0{,}687$. Да, на~3~пп ниже прежних $0{,}726$ -- но~это~честные 3~пп. Они~укладываются в~обычную статистическую дисперсию для~val из~893~снимков с~учётом всех~случайных факторов обучения (RandomResizedCrop, перетасовка минибатчей, инициализация головы). Зато~теперь этим числам можно доверять.

\section{Сохранение весов и деплоймент}
\label{sec:deploy}

\texttt{state\_dict} лучшей эпохи я~сохраняю в~\verb|efficientnet_b0_styles.pth| (около 16~МБ) в~Google~Drive, в~каталог \verb|training_out_v3.1/|. Чтобы перенести модель в~ML-сервис, достаточно скопировать файл в~\verb|ml-service/weights/| и~перезапустить контейнер: \verb|docker compose restart ml-service|.

На~старте \texttt{StyleClassifier} сам~находит веса через \verb|_resolve_weights_path()| -- тот~по~очереди проверяет каноничный путь из~конфига, файлы с~префиксом \verb|efficientnet_b0_styles*| и, наконец, любой \verb|*.pth| в~\verb|weights/|. Как~только валидный state\_dict найден, сервис переключается из~эвристического режима в~нейросетевой и~пишет в~лог: \verb|Model loaded: EfficientNet-B0 (weights from ...)|.

Но~главное даже не~в~абсолютных числах:
\begin{enumerate}[label=\arabic{enumi})]
\item порядок классов по~сложности \emph{сохраняется целиком}: \texttt{neon}\,$>$\,\texttt{golden\_hour}\,$>$\,\texttt{vintage/airy}\,$>$\,\texttt{minimalist/dark}\,$>$\,\texttt{dramatic} $\approx$ \texttt{monochrome};
\item одни и~те~же топ-путаницы (\texttt{monochrome}~$\leftrightarrow$~\texttt{minimalist}, \texttt{dramatic}~$\leftrightarrow$~\texttt{dark}~$\leftrightarrow$~\texttt{monochrome}) в~обоих обучениях;
\item распределение предсказаний у~v3.1 ложится в~коридор $[0{,}94;1{,}03]$ от~истинных частот -- даже плотнее, чем~у~v3 ($[0{,}87;1{,}08]$); перекоса нет.
\end{enumerate}

Вывод напрашивается сам: \textbf{ключевые выводы работы -- иерархия классов, структура ошибок, оценка того, какие классы определимы, а~какие нет, -- не~зависят от~конкретного разбиения данных}. Это~свойства самой задачи и~архитектуры, а~не~удачно (или~неудачно) выпавшего split'а. Значит, и~относиться к~полученным числам можно как~к~устойчивым, а~не~как~к~случайности одного прогона.

\section{Интерпретируемость модели методом Grad-CAM}
\label{sec:gradcam}

\subsection{Постановка}

Grad"~CAM (Gradient-weighted Class Activation Mapping)~\cite{Selvaraju:2017} показывает, на~какие участки изображения свёрточная сеть <<смотрит>>, когда выносит предсказание. Получается тепловая карта поверх исходного снимка: где~горячо -- там~модель и~опиралась. Мне это~нужно, чтобы ответить на~важный вопрос: действительно~ли модель ловит стиль -- свет, тона, текстуры, -- или~же~нашла какой-нибудь shortcut вроде формы объектов или~наличия людей в~кадре.

\subsection{Реализация}

Grad"~CAM применён к~последнему свёрточному блоку EfficientNet"~B0 (\verb|model.features[-1]|). Реализация выполнена вручную через хуки PyTorch (\verb|register_forward_hook|, \verb|register_full_backward_hook|), без~зависимости от~внешних библиотек. Алгоритм:

\begin{enumerate}[label=\arabic{enumi})]
\item Прямой проход с~сохранением активаций target-слоя через forward-hook.
\item Обратный проход от~скаляра \verb|logits[0, target_class]|; gradient выходов target-слоя сохраняется через backward-hook.
\item Глобальное усреднение градиентов по~пространственным осям даёт вес каждого канала.
\item Линейная комбинация активаций с~этими весами, ReLU-обрезка, билинейный upsample до~разрешения входа, нормализация в~$[0;1]$.
\end{enumerate}

Сгенерированы три типа артефактов: по~шесть изображений на~каждый класс с~heatmap-наложением, общая сетка 8$\times$6 для~одной страницы отчёта, галерея <<уверенно неправильных>> предсказаний (топ-10 misclassifications по~confidence) с~heatmap по~\emph{предсказанному} классу -- иными словами, видна область, на~которую модель <<смотрела>>, когда ошибалась.

\subsection{Результаты}

Общая сетка Grad"~CAM-визуализаций по~восьми классам приведена на~рис.~\ref{fig:gradcam_grid}.

\begin{figure}[!ht]
\centering
\includegraphics[width=\textwidth]{gradcam/gradcam_grid.png}
\caption{Grad-CAM heatmap'ы для шести представителей каждого класса. По строкам: airy, dark, dramatic, golden\_hour, minimalist, monochrome, neon, vintage}
\label{fig:gradcam_grid}
\end{figure}

И~картина обнадёживает -- модель действительно смотрит туда, куда нужно:

\begin{itemize}
\item \texttt{golden\_hour}: heatmap концентрируется на~тёплых засветах неба, контурном свете объектов, бликах -- что~совпадает с~определением класса через цветовую температуру.
\item \texttt{neon}: фокус на~ярких насыщенных пятнах источников света (вывески, лампы) на~тёмном фоне; внимание игнорирует второстепенные участки кадра.
\item \texttt{airy}: модель смотрит на~светлые области (небо, светлый фон), а~не~на~центральные объекты; это~согласуется с~операциональным определением через высокую яркость.
\item \texttt{dark}: внимание сконцентрировано на~переходах между светом и~тенью, а~не~на~средне-яркостных областях.
\item \texttt{monochrome}: внимание распределено равномерно по~всему кадру -- что~ожидаемо, поскольку определяющий признак (отсутствие насыщенности) присутствует на~всех пикселях.
\end{itemize}

Галерея высокоуверенных ошибок (рис.~\ref{fig:gradcam_errors}) предоставляет качественное объяснение типичных промахов модели:

\begin{figure}[!ht]
\centering
\includegraphics[width=\textwidth]{gradcam/gradcam_errors.png}
\caption{Топ-10 уверенно неправильных предсказаний с heatmap по предсказанному классу}
\label{fig:gradcam_errors}
\end{figure}

Типовые сюжеты ошибок:
\begin{itemize}
\item \emph{Чёрно-белый портрет в~низком ключе}: истинный класс \texttt{dark}, предсказание \texttt{monochrome}. Модель уверена в~отсутствии цвета и~отбрасывает фактор низкой яркости. Это~композитный случай -- фотография действительно одновременно тёмная и~монохромная; single-label постановка вынуждает выбрать одно.
\item \emph{Флакон духов на~тёмном минималистичном фоне}: истинный класс \texttt{dark}, предсказание \texttt{minimalist}. Модель видит изолированный центральный объект на~большом негативном пространстве и~интерпретирует это~как минимализм, игнорируя тональную характеристику.
\item \emph{Чёрно-белый высококонтрастный снимок}: истинный \texttt{dramatic}, предсказание \texttt{monochrome}. Признак отсутствия цвета доминирует над~признаком контраста.
\end{itemize}

По~большому счёту это~и~не~ошибки -- скорее, симптом \emph{фундаментального ограничения single-label}: у~композитного снимка любой единственный ярлык неизбежно отбрасывает часть правды. Именно эти~примеры окончательно убедили меня перейти к~multi-label (раздел~\ref{sec:multilabel}).

\section{Качество embedding-пространства}
\label{sec:embed_quality}

\subsection{Постановка}

Те~самые 1280-мерные эмбеддинги, что~снимаются перед классифицирующей головой, backend использует для~поиска похожих снимков через cosine similarity (раздел~\ref{sec:mlservice}). Но~у~них~есть и~исследовательская ценность: если~посмотреть, как~они~раскладываются по~классам в~низкоразмерной проекции, можно проверить -- выучила~ли модель именно стиль, или~зацепилась за~что-то поверхностное.

\subsection{Методология}

Эмбеддинги извлечены для~всей val-выборки (893~вектора по~1280~компонент). Применены три инструмента анализа:

\begin{enumerate}[label=\arabic{enumi})]
\item Метрика \emph{silhouette score} в~cosine-пространстве: оценивает, насколько каждый пример ближе к~своему кластеру, чем к~чужим. Диапазон $[-1;+1]$, $>\,0{,}3$ обычно интерпретируется как <<хорошо разделимо>>.
\item Метрика \emph{Davies-Bouldin index}: отношение внутрикластерной дисперсии к~межкластерной; меньшее значение лучше.
\item \emph{k-NN classifier accuracy} (cosine-метрика, $k=5$, 5-fold CV): прямая мера качества представлений как признаков для~классификации, без~обучения дополнительных слоёв.
\end{enumerate}

Дополнительно построены 2D-проекции через t"~SNE (perplexity~30, init~PCA) и~UMAP (n\_neighbors~15, min\_dist~0{,}1) и~матрица cosine similarity между центроидами классов.

Davies-Bouldin~$=6{,}24$ говорит о~том~же -- разброс внутри кластеров велик на~фоне расстояний между ними. Поначалу это~настораживает.

Но~k-NN на~сырых эмбеддингах даёт $0{,}618$ -- всего на~$\sim$\,7~пп ниже полноценного дообученного классификатора ($0{,}694$). А~это~уже~совсем другой вывод: \emph{основная классифицирующая способность сидит в~самих представлениях}, а~не~в~финальной линейной голове. То~есть эмбеддинги хороши и~для~поиска похожих, и~для~любых downstream-задач -- кластеризации, аннотирования, кросс-модального поиска. Низкий~же silhouette объясняется не~плохими представлениями, а~природой стиля: классы и~должны перекрываться.

Это~хорошо видно на~матрице центроидной близости (рис.~\ref{fig:centroids}): \texttt{monochrome} жмётся к~\texttt{minimalist}, \texttt{vintage} и~\texttt{dark}, а~\texttt{dark} -- к~\texttt{dramatic}. Картина буквально повторяет структуру ошибок из~confusion matrix. Получается, путаница рождается не~в~классифицирующей голове, а~ещё~глубже -- на~уровне представлений, где~классы перекрываются по~самому своему стилевому содержанию.

\section{Базовая классификация на низкоуровневых признаках}
\label{sec:scorecard}

\subsection{Постановка}

Здесь я~проверяю гипотезу из~раздела~\ref{sec:problem}: что~мои~классы и~правда определимы через простые статистики изображения. Логика проверки такая. Если~гипотеза верна, то~примитивный классификатор на~пяти ручных признаках (score-card) обязан заметно обогнать случайное гадание ($1/8\approx 0{,}125$), но~при~этом столь~же заметно уступить глубокой сети. А~разница между этим baseline и~CNN как~раз и~покажет, сколько добавляют глубокие представления поверх <<очевидных>> характеристик -- то~есть нужна~ли вообще тяжёлая модель.

\subsection{Методология}

\paragraph{Baseline-классификация.} Обучены два классификатора на~train-множестве, использующие только пять score-card-признаков: логистическая регрессия со~стандартизацией и~Random Forest на~300~деревьях. Оценка точности на~val-множестве.

\section{Калибровка апостериорных вероятностей}
\label{sec:calibration}

\subsection{Постановка}

Свёрточные сети, обученные с~cross-entropy, обычно \emph{переуверены}~\cite{Guo:2017} -- завышают уверенность по~сравнению с~реальной точностью. Для~интерфейса это~важно: я~показываю пользователю проценты, и~хочется, чтобы <<90\,\%>> действительно означали примерно 90\,\% правильных ответов на~этом уровне, а~не~65. В~этом эксперименте я~проверяю, насколько хорошо v3.1 откалибрована, и~поправляю её~через temperature scaling.

\subsection{Методология}

\paragraph{Метрики.}
\begin{itemize}
\item \emph{Expected Calibration Error (ECE)} -- средневзвешенная разность между средним confidence и~accuracy по~бакетам uniformly-splittted confidence, 15 бакетов.
\item \emph{Maximum Calibration Error (MCE)} -- максимальная разность по~бакетам.
\item \emph{Brier score} -- средний квадрат отклонения предсказанного распределения от~one-hot истинного.
\item \emph{Negative Log-Likelihood (NLL)} -- log-loss на~val-множестве.
\end{itemize}

\paragraph{Подходы к калибровке.}
\begin{enumerate}[label=\arabic{enumi})]
\item \emph{Скалярное temperature scaling}: подбор одного скаляра $T > 0$, делящего logits, через LBFGS-оптимизацию NLL на~val-множестве.
\item \emph{Векторное (per-class) scaling}: подбор отдельного $T_c$ для~каждого класса; даёт больше степеней свободы и~чувствительнее к~разной асимметрии переуверенности.
\end{enumerate}

\subsection{Результаты}

Скалярная температура нашлась равной $T = 1{,}094$ -- то~есть v3.1 переуверена лишь чуть-чуть (у~явно переуверенных моделей $T$ доходит до~$1{,}5$-$2{,}5$). Вектор по-классам интереснее: $T_c \in [0{,}746;\,1{,}338]$, причём максимумы приходятся на~\texttt{minimalist} и~\texttt{dark} (там~модель переуверена), а~минимумы -- на~\texttt{neon} и~\texttt{golden\_hour} (тут~она, наоборот, скорее осторожничает). Интересно, что~скалярная калибровка ECE не~улучшила, а~даже чуть~ухудшила -- с~$0{,}061$ до~$0{,}065$. Логично: один общий множитель не~может учесть, что~разные классы переуверены по-разному. А~вот векторная калибровка сработала -- ECE упал в~$\sim$\,$1{,}25$ раза (до~$0{,}049$), MCE -- в~$\sim$\,$1{,}5$ раза (до~$0{,}300$). Её~я~и~рекомендую для~деплоя: на~практике это~значит хранить рядом с~весами вектор $T_c$ из~восьми чисел и~делить на~него logits перед softmax.

Стоит это~копейки: $T_c$ -- восемь чисел в~текстовом файле, плюс одно поэлементное деление на~инференс. Accuracy при~этом просела всего на~$\sim$\,0{,}6~пп (с~$0{,}694$ до~$0{,}688$) -- нормальная плата за~честные проценты: модель чуть~реже бьёт <<в~точку>>, зато~её~уверенность теперь можно понимать буквально.

\section{Сравнение с foundation-моделью CLIP}
\label{sec:clip}

\subsection{Постановка}

CLIP ViT"~B/32~\cite{Radford:2021} -- это~foundation-модель от~OpenAI, обученная на~$\sim$\,400~миллионах пар <<изображение -- текст>>. Её~image-encoder выдаёт 512-мерные представления, которые на~удивление хорошо работают <<из~коробки>> для~самых разных задач, включая стилевую категоризацию. Мне~стало любопытно, насколько моя~специально дообученная сеть выигрывает у~такой~универсальной модели -- и~выигрывает~ли вообще.

Эксперимент сравнивает три подхода к~стилевой классификации:
\begin{enumerate}[label=\arabic{enumi})]
\item собственная модель EfficientNet"~B0 v3.1, дообученная на~3556~фотографиях ($\sim$\,30~минут T4);
\item linear probe поверх замороженных представлений CLIP -- логистическая регрессия на~512-мерных image embeddings (обучение $<\,1$~минуты на~CPU);
\item zero-shot классификация через текстовые prompt'ы (<<a~\{style\}~photo>>, без~использования размеченных данных).
\end{enumerate}

\subsection{Методология}

\paragraph{Linear probe.} CLIP ViT"~B/32 предобученный от~OpenAI загружен через библиотеку \texttt{open\_clip\_torch}. Все 4449~изображений (train и~val) прокодированы image-encoder'ом, нормализованы. Поверх train-embeddings обучена \texttt{LogisticRegression} ($C=1$, max\_iter$=2000$). Оценка на~val.

\paragraph{Zero-shot.} Для каждого класса сформирован набор из~трёх текстовых prompt'ов (например, для~\texttt{neon}: <<a~neon-lit photograph with vibrant colors>>, <<a~cyberpunk neon photograph at~night>>, <<a~photo with bright neon lights>>). Embeddings prompt'ов усреднены, нормализованы. Для~каждого val-изображения предсказание~--- \texttt{argmax} cosine similarity с~текстовыми центроидами классов.

\paragraph{Linear probe против fine-tune.} И~вот~неожиданность: CLIP linear probe обошёл мою дообученную EfficientNet"~B0 на~$+4{,}4$~пп по~accuracy и~$+4{,}3$~пп по~macro F1 -- без~всякого обучения на~GPU, за~$\sim$\,30~секунд работы sklearn'а. Причём обошёл на~\emph{всех} классах без~исключения, а~сильнее всего на~\texttt{dramatic} ($+8{,}5$~пп). Объяснение простое: представления CLIP, выученные на~сотнях миллионов пар <<картинка -- текст>>, изначально ближе к~стилевой семантике, чем~ImageNet-представления, заточенные под~объекты. Честно говоря, для~собственной модели это~результат не~из~приятных -- но~прятать его~я~не~стану, в~этом и~есть смысл сравнения.

\paragraph{Чем приходится платить.} CLIP весит $\sim$\,350~МБ против $\sim$\,16~МБ у~EfficientNet"~B0, а~на~CPU считает один кадр $\sim$\,$300$~мс вместо $\sim$\,$50$. Для~сервиса с~CPU-инференсом это~ощутимо. Плюс параметров там~на~порядки больше, и~разбираться в~отдельных компонентах сложнее.

\paragraph{Zero-shot.} Совсем без~размеченных данных CLIP zero-shot выбивает $63{,}5\%$ -- на~уровне ручного score-card-baseline и~заметно выше случайного гадания. Но~по~классам разброс огромный: \texttt{neon} (F1~$=0{,}934$) и~\texttt{golden\_hour} (F1~$=0{,}793$) почти как у~linear probe, а~\texttt{dramatic} (F1~$=0{,}244$) -- провал. Дело в~<<текстуальности>> понятия: про~неон и~золотой час в~интернете написаны миллионы подписей, а~<<dramatic>> -- абстракция без~устоявшегося лексикона, и~текстовому энкодеру не~за~что зацепиться.

\paragraph{Что в~итоге.} В~текущей системе я~оставил EfficientNet"~B0 -- она~компактнее и~быстрее, а~для~прототипа на~CPU это~решающе. Но~CLIP linear probe -- очевидный следующий шаг, как~только появится GPU-сервер; теперь я~хотя~бы знаю, какого качества от~него ждать.

\section{Multi-label расширение задачи}
\label{sec:multilabel}

\subsection{Постановка}

К~этому эксперименту меня подвели все~предыдущие. Single-label (раздел~\ref{sec:problem}) для~значительной части снимков просто неверна: кадр бывает одновременно и~\texttt{monochrome} (по~цвету), и~\texttt{minimalist} (по~композиции), бывает и~\texttt{dark}, и~\texttt{dramatic} сразу. Загоняя всё~в~один ярлык, я~искусственно сталкивал классы лбами и~занижал потолок качества.

Multi-label снимает это~ограничение -- у~снимка может быть сразу несколько активных меток с~независимыми уверенностями. Гипотеза, которую я~хотел проверить: переход к~multi-label заметно поднимет F1 на~композитных классах (\texttt{monochrome}, \texttt{dark}, \texttt{dramatic}) -- возможно, ценой небольшой просадки на~тех, что~и~так~были чётко изолированы (\texttt{neon}, \texttt{golden\_hour}).

\subsection{Методология}

\paragraph{Откуда взять multi-label разметку.} По-хорошему её~надо размечать вручную -- но~это~$\sim$\,4500~снимков на~каждого аннотатора, что~для~дипломной работы нереально. Поэтому я~пошёл на~компромисс: расширил исходные single-label метки автоматически, детерминированными правилами на~базе score-card. Для~каждой фотографии:
\begin{enumerate}[label=\arabic{enumi})]
\item Сохраняется исходная gold-метка из~папки класса.
\item Дополнительные метки активируются по~правилам:
\begin{itemize}
\item \texttt{monochrome}, если saturation $<\,0{,}10$;
\item \texttt{dark}, если brightness $<\,0{,}30$;
\item \texttt{airy}, если brightness $>\,0{,}70$ и~contrast $<\,0{,}45$;
\item \texttt{dramatic}, если contrast $>\,0{,}70$;
\item \texttt{golden\_hour}, если warmth $>\,0{,}62$ и~brightness $>\,0{,}45$ и~saturation $>\,0{,}25$;
\item \texttt{neon}, если saturation $>\,0{,}65$ и~brightness $<\,0{,}45$.
\end{itemize}
\item Разрешаются конфликты типа \texttt{airy} $\leftrightarrow$ \texttt{dark}, не~более четырёх активных меток на~фотографию.
\end{enumerate}

\paragraph{Статистика результирующей разметки.} После применения правил $56{,}8\%$ изображений получили $\geq 2$ активных меток. Распределение по~количеству позитивов на~класс приведено в~таблице~\ref{tab:colabels}.

Самое показательное -- \texttt{monochrome}: из~\emph{худшего} класса в~v3.1 он~стал \emph{лучшим} в~v4, с~F1$=0{,}934$ и~AP$=0{,}987$. По~сути это~верхняя планка того, чего можно добиться для~операционально определимого класса при~правильной постановке.

\paragraph{Чем пришлось пожертвовать.} \texttt{neon}: $-6{,}6$~пп; \texttt{golden\_hour} и~\texttt{vintage}: по~$-2{,}1$~пп. Эти классы и~так~были изолированы, для~них single-label работала корректно, и~расширение разметки только подмешало им~шум через автоматические ложноположительные. Впрочем, у~\texttt{neon} AP остаётся высоким ($0{,}916$) -- просадка F1 идёт от~выбранного порога $\theta_{neon}=0{,}85$, при~котором precision важнее recall.

\paragraph{Если смотреть в~целом.} Macro F1 вырос с~$0{,}687$ (v3.1) до~$0{,}773$ (v4) -- плюс $8{,}6$~пп. Hamming accuracy $0{,}920$ значит, что~из~$893 \times 8 = 7144$ бинарных решений модель верно принимает $92\%$. А~exact-match $0{,}529$ -- что~для~$53\%$ снимков она~угадывает весь~набор меток целиком, без~единой ошибки.

\paragraph{Где здесь слабое место.} Не~буду делать вид, что~всё~идеально: автоматическая разметка -- не~замена ручной. Пороги в~правилах я~подбирал на~глаз, и~они~могут расходиться с~тем, что~сказал~бы эксперт. Для~настоящего production-деплоя multi-label стоит разметить вручную $\sim$\,500-1000~снимков и~откалибровать пороги уже~на~них. Но~даже в~таком виде эксперимент чётко показывает направление и~задаёт эмпирическую верхнюю границу качества -- а~это~и~было его~целью.

\section{Масштабирование в production-окружении}
\label{sec:production}

При~переходе от~демонстрационной к~production-инсталляции необходимы следующие изменения:

\begin{enumerate}[label=\arabic{enumi})]
\item \textbf{Секреты.} Значения \verb|JWT_SECRET|, паролей PostgreSQL и~MinIO выносятся из~\verb|docker-compose.yml| в~secrets-хранилище CI/CD (HashiCorp Vault, AWS Secrets Manager) и~прокидываются через переменные окружения при~деплое.
\item \textbf{TLS-терминация.} Обратный прокси (nginx, Traefik) с~Let's Encrypt-сертификатом перед backend'ом; HTTP-трафик редиректится на~HTTPS. CORS-политика обновляется со~списка \verb|localhost|-origin'ов на~production-домен.
\item \textbf{Управляемая СУБД.} PostgreSQL переносится в~managed-сервис (AWS RDS, Yandex Cloud Managed PostgreSQL); регулярные бэкапы, репликация, мониторинг -- из~коробки. Backend меняет только endpoint в~\verb|application.yml|.
\item \textbf{Объектное хранилище.} MinIO заменяется на~AWS~S3 или~совместимое managed-решение; API-совместимость SDK обеспечивает миграцию без~изменений в~Java-коде.
\item \textbf{Оркестрация.} Docker Compose заменяется на~Kubernetes. Для~каждого сервиса создаётся пара Deployment+Service; PostgreSQL/MinIO/RabbitMQ -- StatefulSets с~PersistentVolumeClaim либо internal endpoints managed-сервисов. Образы переиспользуются без~пересборки.
\item \textbf{Мониторинг и алертинг.} Подключается Prometheus с~Spring Boot Actuator для~JVM-метрик, micrometer-экспортер для~ML-сервиса. Grafana-дашборды для~latency перцентилей, error rate, заполнения очереди. Alerting через Alertmanager на~аномальные метрики (медианное время классификации $>\,5$~с, более 5\% \texttt{FAILED}-статусов и~т.\,д.).
\item \textbf{Логирование.} Stdout-логи всех контейнеров собираются Fluent~Bit и~отправляются в~ELK-стек или~Loki. Заведена корреляция запросов через MDC-поле \verb|X-Request-Id|, прокидываемое из~клиента через backend в~AMQP-заголовки.
\end{enumerate}

\section{Информационная безопасность}
\label{sec:security}

Здесь я~собрал воедино меры безопасности, которые уже~встроены в~систему, и~честно перечислил то, что~пока~не~закрыто. Ориентировался на~ключевые категории OWASP Top~10.

\subsection{Аутентификация и управление сессиями}

Пароли пользователей хранятся в~виде BCrypt-хешей со~strength~10. Алгоритм устойчив к~атакам по~словарю и~rainbow tables; параметр strength соответствует современным рекомендациям OWASP (2024). Аутентификация выполняется через JWT с~алгоритмом HS512 и~TTL~24~часа. Серверные сессии отсутствуют, что~устраняет уязвимости session fixation и~session hijacking.

\subsection{Авторизация}

Все запросы к~ресурсам пользователя выполняются с~фильтрацией по~\verb|user_id| на~уровне SQL-запроса в~репозитории (метод \verb|findByIdAndUserId|). Это~закрывает Insecure Direct Object Reference (IDOR) и~Horizontal Privilege Escalation на~уровне кода, а~не~бизнес-логики: пользователь не~может обратиться к~чужой фотографии даже зная её~идентификатор. При~неавторизованном запросе возвращается код~400 (<<not found>>), а~не~403, что~не~раскрывает факт существования чужого ресурса.

\subsection{Валидация ввода}

Все входные DTO покрыты Bean Validation (\verb|@NotBlank|, \verb|@Email|, \verb|@Size|). Загрузка изображений валидирована по~MIME-типу (whitelist \verb|image/jpeg|, \verb|image/png|, \verb|image/webp|) и~размеру (\verb|spring.servlet.multipart.max-file-size: 25MB|).

\subsection{SQL-инъекции и XSS}

SQL-инъекции исключены по~конструкции: все запросы выполняются через JPA с~параметризацией; ручная конкатенация SQL-строк отсутствует. XSS-уязвимости купированы стандартным эскейпом React (\verb|innerHTML| не~используется); presigned-URL'ы и~метаданные изображений не~содержат HTML-контента.

\subsection{CSRF}

CSRF-защита отключена осознанно. Обоснование: API не~использует cookie-сессий (только Authorization-заголовок), что~исключает классический CSRF-вектор. Браузер не~прикрепляет JWT к~сторонним запросам автоматически.

\subsection{Транспортная безопасность}

В~текущей реализации CORS настроен на~список \verb|localhost|-origin'ов для~разработки. В~production добавляется TLS-терминация через reverse proxy (см.~раздел~\ref{sec:production}).

\subsection{Не реализовано (направления развития)}

Не~буду делать вид, что~система защищена идеально. Вот~что~я~сознательно оставил за~рамками прототипа, но~что~обязательно стоит добавить перед~production:

\begin{itemize}
\item \emph{Rate limiting} на~\verb|/api/auth/login| -- защита от~brute-force подбора пароля. Реализация через Bucket4j (Java) или~nginx \verb|limit_req|.
\item \emph{Refresh-токены и~revocation list} -- возможность принудительного логаута без~ожидания истечения TTL (на~текущий момент 24~часа). Реализация через Redis-blacklist с~TTL до~истечения исходного JWT.
\item \emph{Audit log} -- логирование критичных действий (вход, удаление фото, изменение профиля) в~отдельную таблицу для~постфактумного аудита.
\item \emph{Антивирусная проверка} загруженных файлов через ClamAV-sidecar; проверка изображений на~корректность заголовков (Pillow-верификация) перед передачей в~MinIO.
\item \emph{Content Security Policy headers} на~frontend; \texttt{X-Frame-Options}, \texttt{X-Content-Type-Options} на~backend-ответах.
\item \emph{Дифференциальная приватность} в~публичном embedding-API (если~будет открыт): добавление контролируемого шума, чтобы исключить инверсионные атаки на~приватность пользователей.
\end{itemize}

\section{Направления дальнейшего развития}
\label{sec:future_work}

Эксперименты не~только дали результаты, но~и~подсказали, куда двигаться дальше. Я~выделил шесть направлений -- от~самых приоритетных до~перспективных.

\paragraph{Ручная multi-label разметка.} Главное методологическое улучшение -- замена автоматически сгенерированной multi-label разметки на~ручную аннотацию $\sim$\,1000~фотографий тремя-пятью экспертными аннотаторами с~оценкой межрейтинговой согласованности (Cohen's $\kappa$, Krippendorff's $\alpha$). Это~устранит зависимость от~порогов score-card и~даст истинную верхнюю границу качества multi-label постановки.

\paragraph{Переход на CLIP linear probe в production.} По~результатам раздела~\ref{sec:clip} CLIP linear probe превосходит EfficientNet"~B0 fine-tune на~4{,}4~пп при~отсутствии переобучения. При~переходе на~GPU-инференс (что~снимает ограничение размера модели и~времени инференса) рекомендуется внедрить CLIP как production-модель, оставив EfficientNet"~B0 как fallback для~CPU-окружений.

\paragraph{Fine-tune CLIP методом LoRA.} Следующий уровень -- параметр-эффективное дообучение CLIP через Low-Rank Adaptation~\cite{Hu:2022}. Дообучение лишь $\sim$\,$0{,}1\%$ параметров (адаптеров вокруг attention-слоёв) позволит сохранить компактность развёртывания и~получить дополнительное улучшение качества на~собственном датасете.

\paragraph{Векторный поиск через pgvector.} Текущая реализация поиска похожих фотографий выполняется брутфорсом за~$O(N \cdot 1280)$ в~Java-коде сервиса. Для~коллекций $>\,10\,000$ фотографий рекомендуется переход на~расширение PostgreSQL \texttt{pgvector} с~HNSW-индексом: запрос становится $O(\log N)$ и~остаётся в~базе данных без~введения дополнительного сервиса (Qdrant, Weaviate).

\paragraph{Stratified k-fold cross-validation.} Для~повышения статистической надёжности per-class метрик -- замена единственного train/val split на~5-fold stratified CV. Это~увеличит время обучения в~пять раз, но~даст доверительные интервалы для~каждой метрики и~снизит чувствительность к~случайному разбиению (особенно для~классов \texttt{dark} и~\texttt{minimalist}, см.~раздел~\ref{sec:robustness}).

\paragraph{Persistent split с сохранением в Drive.} Урок из~истории v3~$\to$~v3.1 (см.~раздел~\ref{sec:reproduce}): split должен сохраняться вместе с~весами в~постоянное хранилище, а~не~в~эфемерную файловую систему среды обучения. Технически -- сохранение списка путей train/val в~JSON-файл рядом с~\verb|*.pth| в~Google~Drive или~S3-бакете. Эта~мера предотвращает ситуацию data leakage, обнаруженную в~процессе настоящей работы.

\chapternonum{Заключение}

В~рамках этой работы я~спроектировал и~реализовал систему автоматической классификации фотографий по~визуальному стилю на~основе transfer learning, а~затем разобрал её~ключевой компонент -- свёрточную сеть -- куда подробнее, чем~обычно требуется от~дипломного прототипа.

Все~задачи, поставленные во~введении, выполнены:

\begin{enumerate}[label=\arabic{enumi})]
\item Проведён обзор современных методов классификации изображений, существующих программных продуктов-аналогов и~технологического стека (гл.~\ref{ch:design}, разделы~\ref{sec:methods}, \ref{sec:competitors}, \ref{sec:stack}). Обоснован выбор архитектуры EfficientNet"~B0 для~production-инсталляции и~CLIP ViT"~B/32 для~сравнительного эксперимента.
\item Собран и~размечен датасет из~4691~фотографии в~восьми стилевых категориях; проведена MD5-дедупликация и~балансировка до~распределения с~отношением max/min~$=1{,}2$ (гл.~\ref{ch:dataset}, разделы~\ref{sec:collection}, \ref{sec:preprocess}).
\item Проведено три итерации дообучения модели EfficientNet"~B0 (v1, v2, v3) с~поэтапной коррекцией таксономии классов; в~ходе подготовки исследовательской части выявлено и~устранено data leakage в~оригинальном split'е, проведено повторное обучение на~воспроизводимом разделении (v3.1, разделы~\ref{sec:training}, \ref{sec:reproduce}). Финальная модель достигает val~accuracy$=0{,}694$, macro F1$=0{,}687$.
\item Спроектирована и~реализована микросервисная архитектура из~пяти компонентов с~асинхронным взаимодействием через AMQP-брокер (главы~\ref{ch:design}, \ref{ch:implementation}).
\item Реализован REST-API из~десяти эндпоинтов с~аутентификацией через JWT и~фильтрацией по~владельцу на~уровне SQL-запросов (раздел~\ref{sec:api}).
\item Реализовано клиентское веб-приложение с~brutalist-дизайном, masonry-сеткой, цветовой фильтрацией и~поиском похожих фотографий через embedding-сходство (раздел~\ref{sec:frontend}).
\item Обеспечена контейнеризация всех компонентов и~автоматизированное развёртывание через Docker Compose (раздел~\ref{sec:infrastructure}). Настроена непрерывная интеграция через GitHub Actions; покрытие интеграционными тестами через Testcontainers составляет 11~тестов (раздел~\ref{sec:functional}).
\item Проведены шесть исследовательских экспериментов (E1-E6) с~углублённым анализом свойств обученной модели (разделы~\ref{sec:gradcam}-\ref{sec:multilabel}); по~их~результатам получены новые методологические выводы.
\item Сформулированы шесть направлений дальнейшего развития системы и~модели (раздел~\ref{sec:future_work}).
\end{enumerate}

\textbf{Если выделить главное из~исследовательской части -- пять результатов.}

\begin{itemize}
\item Ключевые выводы -- иерархия сложности классов, структура ошибок, оценка того, какие категории определимы, -- \emph{устойчивы к~случайной перетасовке валидационной выборки}: между двумя независимыми обучениями per-class F1 меняются не~больше чем~на~$9$~пп, а~порядок классов и~топ-путаницы держатся. Значит, это~свойства самой задачи и~архитектуры, а~не~везения с~конкретным разбиением (раздел~\ref{sec:robustness}).
\item Введённая в~работе таксономия восьми классов \emph{операционально определима через статистики низкоуровневых признаков}: ANOVA по~пяти score-card-метрикам даёт $F$-статистики 70-501 при~$p \ll 0{,}001$, baseline-классификатор на~ручных признаках достигает $48{,}9\%$ accuracy. Применение глубокой свёрточной сети добавляет $\sim$\,$20$ процентных пунктов сверх этого -- что~оправдывает её~использование (раздел~\ref{sec:scorecard}).
\item \emph{Foundation-модель CLIP linear probe превосходит дообученную EfficientNet"~B0} на~$+4{,}4$~пп accuracy и~$+4{,}3$~пп macro F1 при~отсутствии GPU-обучения и~использовании только sklearn-логистической регрессии. Это~подтверждает превосходство представлений foundation-моделей над~ImageNet-весами для~стилевой задачи (раздел~\ref{sec:clip}).
\item \emph{Переход на~multi-label постановку задачи трансформирует ранее самый слабый класс} \texttt{monochrome} (F1$=0{,}545$ в~single-label) в~самый сильный (F1$=0{,}934$, AP$=0{,}987$ в~multi-label, $+38{,}9$~пп). Аналогичные значительные улучшения на~классах \texttt{dark} ($+28{,}3$~пп) и~\texttt{dramatic} ($+7{,}3$~пп) -- эмпирическое подтверждение того, что~single-label постановка была методологически некорректна для~композитных классов (раздел~\ref{sec:multilabel}).
\item Метод Grad"~CAM подтверждает, что~модель опирается на~стилистически осмысленные области изображения (засветы для~\texttt{golden\_hour}, насыщенные пятна для~\texttt{neon}, равномерное распределение внимания для~\texttt{monochrome}), а~не~на~shortcut-паттерны. Анализ <<уверенно неправильных>> предсказаний предоставляет качественное объяснение топ-путаниц confusion matrix (раздел~\ref{sec:gradcam}).
\end{itemize}

Результаты работы применимы в~системах курации цифровых фотоархивов, в~исследовательских прототипах по~компьютерному зрению и~как~учебный материал по~глубокому обучению. Весь~исходный код, обученные веса и~артефакты экспериментов я~выложил под~лицензией MIT -- так~что~работу можно не~только повторить, но~и~развивать дальше.

\chapter{Реализация классификатора}
\label{app:classifier}

Ниже приведён ключевой фрагмент Python-кода ML-сервиса -- метод инференса с~извлечением эмбеддинга и~softmax-вероятностей за~один прямой проход.

\begin{lstlisting}[language=Python,basicstyle=\ttfamily\footnotesize,frame=single,caption={Метод \texttt{\_nn\_inference} класса \texttt{StyleClassifier}},label=lst:nn_inference]
def _nn_inference(self, img: Image.Image
                  ) -> Tuple[List[float], List[float]]:
    """Прогон через EfficientNet с извлечением эмбеддинга
    предпоследнего слоя.

    Возвращает (softmax-вероятности по классам,
                1280-мерный embedding).
    """
    with torch.no_grad():
        x = self.transform(img).unsqueeze(0).to(self.device)

        # Расщепляем forward на backbone + head, чтобы
        # извлечь pooled features.
        # EfficientNet: features -> avgpool -> classifier
        feats = self.model.features(x)
        pooled = self.model.avgpool(feats)
        pooled_flat = torch.flatten(pooled, 1)        # [1, 1280]
        logits = self.model.classifier(pooled_flat)   # [1, C]

        probs = torch.softmax(logits, dim=1).squeeze(0).cpu().numpy()
        embedding = pooled_flat.squeeze(0).cpu().numpy()

    return [float(p) for p in probs], [float(v) for v in embedding]
\end{lstlisting}

    p_.requires_grad = True

    {"params": backbone_params, "lr": args.lr_backbone},
    {"params": head_params, "lr": args.lr_head},
], weight_decay=args.weight_decay)

for ep in range(1, n_full + 1):
    tr_loss, _ = run_epoch(model, train_loader, criterion,
                           optimizer, device, scaler,
                           train=True, mixup_alpha=args.mixup_alpha)
    vl_loss, vl_acc = run_epoch(model, val_loader, criterion,
                                optimizer, device, scaler, train=False)
    scheduler.step()
    if vl_acc > best_val_acc:
        best_val_acc, no_improve = vl_acc, 0
        torch.save(model.state_dict(),
                   out_dir / f"{args.arch}_styles.pth")
    else:
        no_improve += 1
        if no_improve >= args.patience:
            break  # Early stopping

\chapter{Реализация Grad-CAM}
\label{app:gradcam}

Самостоятельная реализация Grad"~CAM через PyTorch hooks (без~внешних зависимостей):

\begin{lstlisting}[language=Python,basicstyle=\ttfamily\footnotesize,frame=single,caption={Класс \texttt{GradCAM} (training/gradcam\_viz.py)},label=lst:gradcam]
class GradCAM:
    """Grad-CAM на произвольном свёрточном слое."""

    def __init__(self, model: nn.Module, target_layer: nn.Module):
        self.model = model
        self.activations: torch.Tensor | None = None
        self.gradients: torch.Tensor | None = None
        target_layer.register_forward_hook(self._save_activation)
        target_layer.register_full_backward_hook(self._save_gradient)

    def _save_activation(self, module, inp, out):
        self.activations = out.detach()

    def _save_gradient(self, module, grad_in, grad_out):
        self.gradients = grad_out[0].detach()

    def __call__(self, x: torch.Tensor, class_idx: int) -> np.ndarray:
        self.model.zero_grad()
        logits = self.model(x)
        score = logits[0, class_idx]
        score.backward()

        # Глобальное среднее градиентов по пространственным осям
        # даёт веса каналов.
        weights = self.gradients.mean(dim=(2, 3), keepdim=True)
        cam = (weights * self.activations).sum(dim=1, keepdim=True)
        cam = F.relu(cam)
        cam = F.interpolate(cam, size=x.shape[-2:],
                            mode="bilinear", align_corners=False)
        cam = cam.squeeze().cpu().numpy()
        if cam.max() > 0:
            cam = (cam - cam.min()) / (cam.max() - cam.min() + 1e-8)
        return cam
\end{lstlisting}
